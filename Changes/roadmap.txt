Epoch Completion Roadmap Prompt
===============================

Objective
---------
Create a production-ready release of the Epoch runtime that can bootstrap the
engine end-to-end across supported desktop platforms.

Guiding Principles
------------------
1. Preserve the module-first runtime architecture.
2. Prioritize developer ergonomics: fast iteration, self-diagnosing tooling,
   and clear documentation.
3. Keep compatibility surfaces explicit instead of letting old archive code leak
   back into the active engine by accident.

Execution Plan
--------------
Use the following phases as a checklist for future work.

Phase 1 - Repository Audit & Build Health
-----------------------------------------
- [ ] Verify deterministic builds across supported toolchains.
- [ ] Keep CMake presets current and honest.
- [ ] Capture smoke-build logs for the important targets.

Phase 2 - Core Runtime Stabilization
------------------------------------
- [ ] Expand renderer regression coverage for OpenGL, SDL, Raylib, SFML, and software paths.
- [ ] Finish the remaining fragile backend startup/shutdown paths without overcorrecting in the generic multiplexer.
- [ ] Continue tightening task scheduling, reload behavior, and diagnostics.

Phase 3 - Feature Completion
----------------------------
- [ ] Finish the remaining minor unfinished systems carefully.
- [ ] Either complete Vulkan enough to document it as supported or keep it explicitly experimental.
- [ ] Keep input, save/load, and scripting features aligned across the active runtime.

Phase 4 - Tooling & Automation
------------------------------
- [ ] Improve scripted build/test/package flows.
- [ ] Keep docs generation and smoke harnesses easy to run locally.
- [ ] Expand backend telemetry and regression capture tooling.

Phase 5 - Documentation & Release Readiness
-------------------------------------------
- [x] Rebrand the public docs and README to Epoch.
- [x] Move the legacy archive under `Engine/legacy/`.
- [ ] Write a migration note for consumers still relying on older compatibility names.
- [ ] Run a final release-candidate dry run with updated docs and backend smoke coverage.

Acceptance Criteria
-------------------
- Public docs match the actual repo layout and current branding.
- Runtime version helpers, release notes, and README agree on the active release.
- Legacy compatibility code stays archived under `Engine/legacy/` unless a piece
  is intentionally promoted back into the active engine.
- Experimental backends are labeled honestly.
